# 0.3.17 part 2 - the M-LSD merge-repair was cutting into the page

**Status: shipped, repair disabled by default (`MLSD_REPAIR_ENABLED = false`).**

## What it was supposed to do

Cut off a facing page leaf that the detector had absorbed into the quad. A quad covering a
two-page spread should be trimmed back to the page the user is reading.

## What it actually did

Measured by scoring the trace's own `corner_post.quad` (the corner model's output, before
`applyMlsdEvidence`) against the shipped quad. Same photos, same referee, one variable.

| set | photos the repair changed | quad got worse | got better |
|---|---|---|---|
| holdout42 | 20 | **20** | **0** |
| owner110 | 18 | 16 | 2 |

holdout42, the 20 touched photos:

| | LOCK | mean IoU | mean recall |
|---|---|---|---|
| before the repair | **15 / 20** | 0.859 | 0.870 |
| shipped (after repair) | 5 / 20 | 0.766 | 0.772 |

owner110, all 94 scorable photos:

| | IoU >= 0.5 | mean IoU |
|---|---|---|
| before the repair | 54 / 94 (57 %) | 0.538 |
| shipped | 53 / 94 (56 %) | 0.529 |

Four owner110 quads the repair itself had classified as `page` came back classified `shrunk`.

## Why

Recall tracks `1 - strip` almost exactly on both sets, which means the trim removes paper. The
concrete case is `20261115_192321`:

* corner model returns right edge at x = **1148**
* the page (SAM mask) ends at x = **1064**
* the repair cuts at x = **1000**

So the trim landed on an edge *inside* the page - a printed content block - and discarded 64 px
of paper. The fold lines M-LSD finds on these photos are text-block edges, not the gutter.

## The discriminator that did not work

The obvious test is "is the discarded strip printed matter, or blank margin?" A printed strip
would be an absorbed facing leaf (trim is right), a blank one the page's own margin (trim is
wrong). `tooling/h58_trimclass.py` measured edge density in the discarded region against the kept
region on 38 photos across both sets. It does **not** separate the two outcomes: the photos where
the trim helped and the photos where it hurt are both inky, because in both cases the fold is a
text edge. Threshold scan over ink-ratio 0.2..1.2 moved net IoU monotonically from +2.70 to -0.05
with no separation. So the repair is switched off rather than re-thresholded on a signal that is
not there.

## Result of disabling it

holdout42 (42 photos never used for tuning, SAM page mask referee):

| | LOCK (IoU >= 0.85) | mean IoU | mean recall | mean precision |
|---|---|---|---|---|
| 0.3.16 | 7 / 42 (17 %) | 0.637 | 0.672 | 0.902 |
| 0.3.17 as first shipped | 13 / 42 (31 %) | 0.708 | 0.746 | 0.896 |
| **0.3.17 with repair off** | **23 / 42 (55 %)** | **0.756** | 0.797 | 0.896 |

Lock rate at other thresholds, so one cut-off is not doing the arguing:
IoU >= 0.80 **24/42 (57 %)**, >= 0.85 **23/42 (55 %)**, >= 0.90 **18/42 (43 %)**.

Against 0.3.16: **24 photos improved, 3 worsened, 15 unchanged.** The three regressions are the
degenerate quads the new angle gate rejects, whose fallback replacement is smaller.

owner110 (116 photos, its own unchanged oracle): **53/94 (56 %) -> 54/94 (57 %)**, mean IoU
0.529 -> 0.536, detection count unchanged at 103 (79 CORNER_MODEL / 24 CLASSICAL_FALLBACK).

## Rollback

`MLSD_REPAIR_ENABLED = true` in `OpenCvQuadPageDetector`. The rule, its unit tests, its
measurements and its tooling are all still in place.

Reproduce with:

    python tooling\h57_ab_repair.py  --tag h53spread --set holdout42   # holdout, mask referee
    python tooling\h57b_ab_owner.py  --tag h56owner  --set owner110    # owner110, oracle referee
    python tooling\h58_trimclass.py                                    # the failed discriminator
