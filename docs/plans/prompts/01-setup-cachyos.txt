IMPORTANT - WHAT THIS PROMPT DOES NOT DO
The user installs OpenCode and T3 Code BY HAND before running this: they will have CachyOS
up, OpenCode and T3 Code installed, and their opencode.json in place, and T3 Code running

claim success you did not observe.

CRITICAL: CachyOS is Arch-based. It uses pacman/paru, NOT apt. Do not run apt, apt-get,
dpkg, or any Debian/Ubuntu command. If you catch yourself typing apt, stop.

Idempotent: before installing anything, check whether it already exists. Do not reinstall or
overwrite user config. Do not reboot. Do not delete anything.

=== STEP 2B - BOOT HEALTH / GRUB REPAIR (the user reported a broken GRUB) ===

The user says GRUB - the boot menu that lets them choose which OS to start - is broken and they
do not know why. They want it fixed, not just reported.

READ THIS FIRST - the hard limit of what you can do:
You are running INSIDE the booted CachyOS. If the machine boots far enough for you to run, then
GRUB is not completely dead - it is degraded. Three degraded cases are repairable from here:
  - no menu is shown, it boots straight in (timeout 0 / hidden menu)
  - the menu shows but an OS is missing (usually Windows, via os-prober)
  - the wrong entry is default, or the firmware boot order is wrong
If the machine cannot boot at all (grub rescue> prompt, "unknown filesystem", "no such device",
or the firmware falls straight to the BIOS), NO agent can fix that from inside, because nothing
is running. In that case skip to "CASE D" and give the user the exact commands to run from the
CachyOS live USB. Say plainly that you cannot do it for them.

Safety rules for this step - these are boot-critical:
  - NEVER run grub-install or efibootmgr without first identifying the correct disk and ESP.
  - Confirm the ESP path before touching it: findmnt /boot/efi ; findmnt /efi ; findmnt /boot
  - Back up before editing:
        sudo cp -a /etc/default/grub /etc/default/grub.bak.$(date +%s)
        sudo cp -a /boot/grub/grub.cfg /boot/grub/grub.cfg.bak.$(date +%s) 2>/dev/null
  - Change ONE thing, then re-check, then change the next. Do not apply several fixes blind.
  - Do NOT disable Secure Boot, do NOT wipe EFI entries, do NOT reformat any ESP. If a fix
    would need that, stop and ask the user.
  - If Windows is still installed and the user wants to keep booting it, note that a Linux
    install CAN leave Windows unbootable if its EFI entry is overwritten. Warn before any
    grub-install.

2B.1 - DIAGNOSE. Run all of these and report each output:
  sudo efibootmgr -v                      # what the firmware will boot, and in what order
  sudo bootctl status 2>/dev/null         # if systemd-boot is in play instead of GRUB
  findmnt /boot /boot/efi /efi            # where the ESP actually is
  ls /boot                                # kernel/initramfs images present?
  cat /etc/default/grub                   # the real config that generates the menu
  grep -E '^GRUB_(TIMEOUT|TIMEOUT_STYLE|DEFAULT|DISABLE_OS_PROBER|THEME|CMDLINE_LINUX_DEFAULT)' /etc/default/grub
  sudo grub-mkconfig -o /tmp/grub-test.cfg 2>&1 | tail -30
      # This is a DRY RUN into /tmp - it does not touch the real menu. Warnings here
      # ("failed to get canonical path", "os-prober will not be executed") are the diagnosis.
  sudo grep -c '^menuentry' /tmp/grub-test.cfg ; sudo grep '^menuentry' /tmp/grub-test.cfg | head
  ls /sys/firmware/efi >/dev/null 2>&1 && echo "EFI boot" || echo "LEGACY/BIOS boot"
Then classify the fault into ONE of these and say which:

  CASE A - boots straight through, no menu ever appears
    Cause: GRUB_TIMEOUT=0, or GRUB_TIMEOUT_STYLE=hidden, or the menu is drawn off-screen.
    Fix:
        sudo sed -i 's/^GRUB_TIMEOUT=.*/GRUB_TIMEOUT=5/' /etc/default/grub
        sudo sed -i 's/^GRUB_TIMEOUT_STYLE=.*/GRUB_TIMEOUT_STYLE=menu/' /etc/default/grub
        # if TIMEOUT_STYLE is absent, add it:
        grep -q '^GRUB_TIMEOUT_STYLE' /etc/default/grub || echo 'GRUB_TIMEOUT_STYLE=menu' | sudo tee -a /etc/default/grub
        sudo grub-mkconfig -o /boot/grub/grub.cfg
    Then verify: grep 'set timeout' /boot/grub/grub.cfg   (must be non-zero)

  CASE B - menu appears but Windows (or another OS) is missing
    Cause: os-prober is not installed or is disabled - it is DISABLED by default on Arch for
    security reasons, which is exactly why a dual-boot menu loses Windows.
    Fix:
        sudo pacman -S --needed --noconfirm os-prober
        grep -q '^GRUB_DISABLE_OS_PROBER' /etc/default/grub \
          && sudo sed -i 's/^GRUB_DISABLE_OS_PROBER=.*/GRUB_DISABLE_OS_PROBER=false/' /etc/default/grub \
          || echo 'GRUB_DISABLE_OS_PROBER=false' | sudo tee -a /etc/default/grub
        sudo os-prober                     # must now print the Windows partition + label
        sudo grub-mkconfig -o /boot/grub/grub.cfg
    If `sudo os-prober` prints nothing, Windows' EFI files are gone or its partition is not
    mounted-readable (BitLocker!). Report that - it is a different problem, and running
    grub-mkconfig again will not create an entry that does not exist.

  CASE C - menu shows but entries fail to boot: "no such device", "unknown filesystem",
           or it drops to a `grub rescue>` prompt
    Cause: grub.cfg and the installed GRUB core disagree (kernel moved, ESP re-mounted at a
    different path, or a partial upgrade). This needs a reinstall of the GRUB core.
    ONLY do this from the live USB chroot (CASE D workflow) unless the user asks you to do it
    from here, because a wrong grub-install makes the machine unbootable. If you do run it,
    first print and confirm with the user:
        findmnt /boot/efi -o SOURCE,TARGET,FSTYPE     # e.g. /dev/nvme0n1p1 /boot/efi vfat
        lsblk -f                                        # confirm the distro disk
    then:
        sudo grub-install --target=x86_64-efi --efi-directory=/boot/efi --bootloader-id=CachyOS --recheck
        sudo grub-mkconfig -o /boot/grub/grub.cfg
    Never guess the disk name. If /boot/efi is not mounted, mount it first and re-check.

  CASE D - cannot boot at all / you are not running on the machine
    Tell the user to boot the CachyOS live USB, open a terminal, and run this chroot recipe.
    Do NOT run it yourself; hand it over verbatim with the placeholder explained:
        lsblk -f                                  # find the root partition and the ESP
        sudo mount /dev/<ROOT_PART> /mnt
        sudo mount /dev/<ESP_PART>  /mnt/boot/efi  # usually the FAT32 ~300MB partition
        for d in dev proc sys run; do sudo mount --bind /$d /mnt/$d; done
        sudo arch-chroot /mnt
        # inside the chroot:
        grub-install --target=x86_64-efi --efi-directory=/boot/efi --bootloader-id=CachyOS --recheck
        grub-mkconfig -o /boot/grub/grub.cfg
        efibootmgr -v                             # check CachyOS entry exists and is first
        exit
        for d in run sys proc dev; do sudo umount -R /mnt/$d 2>/dev/null; done
        sudo umount -R /mnt
        reboot
    Add: if the firmware still ignores GRUB, use the firmware boot menu (usually F8/F11/F12 at
    power-on) to pick the CachyOS entry once, then fix the order with
        sudo efibootmgr -o 0000,0001              # put the right entry first
    (Read the real numbers from `efibootmgr -v`; do not copy 0000 blindly.)

  CASE E - firmware boot order points at the wrong loader
    Fix, only after reading `efibootmgr -v` and confirming which entry is GRUB:
        sudo efibootmgr -o <grub-entry>,<others...>
    Report the before and after listing.

=== STEP 6 - ROCm on the 9070 XT (gfx1201) - install, then FIX IT IF BROKEN ===

The user has run ROCm on this exact card before, so it should work. But this is a fresh

6a - INSTALL (native first)

6b - CHECKS, in this order. Record the actual output of each:
  1. Device nodes exist and permissions:
       ls -l /dev/kfd /dev/dri/renderD* /dev/dri/card*
       id                                  # needs groups video + render
     If the user is not in video/render, they must re-login. Report it; do not reboot.
  2. Kernel driver is loaded for the card:
       lspci -nnk | grep -A3 -Ei 'vga|display'

     Look for amdgpu binding to the 9070 XT and any firmware/VM errors.
  3. ROCm sees the GPU at all:
       /opt/rocm/bin/rocminfo | head -60
     SUCCESS = an Agent block whose "gfx" target reads gfx1201 (or gfx12xx).
  4. PyTorch sees it (use the ROCm build, not the CPU/default one):
       python -c "import torch; print(torch.__version__, torch.version.hip); print(torch.cuda.is_available()); print(torch.cuda.get_device_name(0))"
     If torch.version.hip prints None, the wheel is the CPU or CUDA build - reinstall from
       https://download.pytorch.org/whl/rocm<ver>   (match the installed ROCm major version)

6c - TROUBLESHOOTING LADDER. Apply one step at a time, re-testing after each, and stop at
the first that works. Report each attempt and its result, including the ones that failed.

  FIX 1 - groups/permissions (most common on a fresh install)
    The user was added to video/render in Step 5 but has not re-logged in. If /dev/kfd is
    root:render only, that alone explains "no GPU". Verify with `id` and report; the fix is a
    re-login, which the user does, not you.

  FIX 2 - ROCm version vs card support
    gfx1201 (RDNA4) needs a recent ROCm (7.x). If rocminfo lists older targets only, check:
      pacman -Q | grep -i rocm
      /opt/rocm/bin/rocminfo | grep -E 'Name|gfx|Marketing'
    If the card is absent entirely, the installed ROCm is too old for RDNA4. Report the exact
    version and move to FIX 5 (Docker), which pins a known-good combination.

  FIX 3 - HSA override (only if the card is detected but agents are empty/unsupported)
    gfx1201 maps to HSA version 12.0.1. Try:
      HSA_OVERRIDE_GFX_VERSION=12.0.1 /opt/rocm/bin/rocminfo | head -40
    and the same env var in front of the PyTorch test. This is a mitigation, not a fix -
    say clearly that it worked around the problem and what it masked.

  FIX 4 - Secure Boot / IOMMU
    If /dev/kfd is missing entirely and dmesg shows nothing for amdgpu:
      sudo dmesg | grep -iE 'kfd|iommu|secure boot' | tail -20
      mokutil --sb-state 2>/dev/null
    Secure Boot blocking the module and restrictive IOMMU groups are both real causes. Report
    what you find and propose the specific change (do NOT edit bootloader config or disable
    Secure Boot without the user's explicit approval).

  FIX 5 - Docker with AMD's official image (the reliable fallback)
      sudo pacman -S --needed --noconfirm docker docker-compose
      sudo systemctl enable --now docker
      sudo usermod -aG docker "$USER"
      sudo docker pull rocm/pytorch:rocm7.14_ubuntu24.04_py3.11_pytorch_release_2.10.0
      sudo docker run --rm --device=/dev/kfd --device=/dev/dri \
          --group-add video --group-add render \
          -e PYTORCH_TUNABLEOP_ENABLED=1 \
          rocm/pytorch:rocm7.14_ubuntu24.04_py3.11_pytorch_release_2.10.0 \
          python -c "import torch; print(torch.__version__); print('cuda available:', torch.cuda.is_available()); print(torch.cuda.get_device_name(0) if torch.cuda.is_available() else 'NO GPU')"
    This route is container-isolated, so it sidesteps host ROCm version mismatches entirely.
    If it works, RUN ALL TRAINING IN THIS CONTAINER and record the exact command in the report.

  FIX 6 - verify it is real, not just "available"
    Whatever route worked, prove the GPU actually computes:
      python - <<'EOF'
      import torch, time
      a = torch.randn(4096, 4096, device='cuda')
      torch.cuda.synchronize(); t0 = time.time()
      for _ in range(20): b = a @ a
      torch.cuda.synchronize(); dt = time.time() - t0
      print('device:', torch.cuda.get_device_name(0))
      print('GFLOP/s:', 20 * 2 * 4096**3 / dt / 1e9)
      EOF
    A real RDNA4 result is in the thousands of GFLOP/s. A tiny number or an error means the
    "available: True" was not real. Report the measured GFLOP/s.
