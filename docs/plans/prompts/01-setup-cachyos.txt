Paste this into OpenCode / T3 Code on the fresh CachyOS machine, BEFORE the project prompt.

IMPORTANT - WHAT THIS PROMPT DOES NOT DO
The user installs OpenCode and T3 Code BY HAND before running this: they will have CachyOS
up, OpenCode and T3 Code installed, and their opencode.json in place, and T3 Code running
with you. This prompt does NOT install, configure or repair those, and does NOT touch
~/.config/opencode/. It verifies they work, then sets up everything else (system packages,

Steps 2 and 9 are verification-only. If OpenCode or your provider config is broken, say so
and stop - the user fixes that, not you.

Work step by step. After EVERY step, show the actual command output that proves it worked.
If a step fails, report the exact error and continue with the next independent step - never
claim success you did not observe.

CRITICAL: CachyOS is Arch-based. It uses pacman/paru, NOT apt. Do not run apt, apt-get,
dpkg, or any Debian/Ubuntu command. If you catch yourself typing apt, stop.

Idempotent: before installing anything, check whether it already exists. Do not reinstall or
overwrite user config. Do not reboot. Do not delete anything.

=== STEP 2B - BOOT CHECK AFTER INSTALL (the user's OLD grub was broken) ===

Background: the user's PREVIOUS boot loader was broken. Entering the firmware menu and picking
the entry by hand, GRUB printed "error: unknown filesystem"; they have been booting that way for
a month. They do NOT want the old install repaired, because installing CachyOS writes a fresh
GRUB core and a NEW EFI entry, which clears that symptom on its own.

So this step is a VERIFY-ONLY check of the NEW boot loader, plus a fix only if a check fails.
Do not repair the old install.

Warn the user BEFORE the install, not after:
  - Calamares: keep "install bootloader" ticked. Without it the machine will not boot on its own.
  - If Windows is also staying on the disk: a Linux install can drop the Windows entry, because
    os-prober is disabled by default on Arch. That is fixed AFTER the install (below) - the
    installer will not do it for you.
  - If Windows is being wiped, ignore the os-prober part entirely.

After the first boot into the new CachyOS, run these and report the output:
  sudo efibootmgr -v                       # a NEW entry (EFI/CachyOS) must exist
  sudo efibootmgr | grep -i bootorder      # is that CachyOS entry the FIRST number?
  findmnt /boot/efi                        # ESP mounted (may be /efi, or /boot itself)
  sudo grep -c '^menuentry' /boot/grub/grub.cfg
  sudo grep 'set timeout' /boot/grub/grub.cfg
  lsblk -f                                 # partition layout, for the record

Then only if a check fails:

  - No CachyOS EFI entry at all:
        findmnt /boot/efi                  # confirm the ESP path FIRST
        sudo grub-install --target=x86_64-efi --efi-directory=/boot/efi \
             --bootloader-id=CachyOS --recheck
        sudo grub-mkconfig -o /boot/grub/grub.cfg
    Never guess the disk or ESP path.

  - CachyOS entry exists but is not first, so the firmware still lands on something stale:
        sudo efibootmgr -v                 # read the real four-digit numbers
        sudo efibootmgr -o <CACHYOS>,<others...>
    Report the BootOrder line before and after. This is the one way the old breakage can still
    bite, so get it right rather than assuming the installer fixed the order.

  - Windows is still installed but missing from the menu:
        sudo pacman -S --needed --noconfirm os-prober
        grep -q '^GRUB_DISABLE_OS_PROBER' /etc/default/grub \
          && sudo sed -i 's/^GRUB_DISABLE_OS_PROBER=.*/GRUB_DISABLE_OS_PROBER=false/' /etc/default/grub \
          || echo 'GRUB_DISABLE_OS_PROBER=false' | sudo tee -a /etc/default/grub
        sudo os-prober                     # must print the Windows partition
        sudo grub-mkconfig -o /boot/grub/grub.cfg
    If os-prober prints nothing, Windows' EFI files are gone or the volume is BitLocker-encrypted.
    Report that; regenerating grub.cfg cannot invent an entry.

  - Dead entries from the old install still clutter the firmware menu (harmless, but one of them
    is the broken one and it may still be what the firmware picks first):
        sudo efibootmgr -v                 # identify by path, e.g. \EFI\<old>\...
        sudo efibootmgr -b <XXXX> -B       # delete ONE stale entry - ONLY with user approval
    Never delete Windows Boot Manager or the new CachyOS entry.

Do NOT grub-install the old install and do NOT chroot anywhere. It is being replaced; its boot
loader is not worth repairing.

Evidence rule: exit code 0 proves nothing about boot. Report the efibootmgr listing, the
BootOrder line, the menuentry count and the timeout. The only real proof is the user rebooting
and reaching the desktop WITHOUT touching the BIOS menu - ask them to do that once.

=== STEP 6 - ROCm on the 9070 XT (gfx1201) - install, then FIX IT IF BROKEN ===

The user has run ROCm on this exact card before, so it should work. But this is a fresh
install on a new distro, and the user has explicitly asked you to FIX GPU problems rather
than just report them. Work down the ladder until `rocminfo` sees gfx1201 and PyTorch
reports the GPU. Diagnose before changing anything, and say what you changed and why.

6a - INSTALL (native first)
  sudo pacman -S --needed --noconfirm rocm-hip-sdk rocm-opencl-runtime rocminfo
  /opt/rocm/bin/hipconfig --version

6b - CHECKS, in this order. Record the actual output of each:
  1. Device nodes exist and permissions:
       ls -l /dev/kfd /dev/dri/renderD* /dev/dri/card*
       id                                  # needs groups video + render
     If the user is not in video/render, they must re-login. Report it; do not reboot.
  2. Kernel driver is loaded for the card:
       lspci -nnk | grep -A3 -Ei 'vga|display'
       dmesg | grep -iE 'amdgpu|gfx' | tail -30
     Look for amdgpu binding to the 9070 XT and any firmware/VM errors.
  3. ROCm sees the GPU at all:
       /opt/rocm/bin/rocminfo | head -60
     SUCCESS = an Agent block whose "gfx" target reads gfx1201 (or gfx12xx).
  4. PyTorch sees it (use the ROCm build, not the CPU/default one):
       python -c "import torch; print(torch.__version__, torch.version.hip); print(torch.cuda.is_available()); print(torch.cuda.get_device_name(0))"
     If torch.version.hip prints None, the wheel is the CPU or CUDA build - reinstall from
       https://download.pytorch.org/whl/rocm<ver>   (match the installed ROCm major version)

6c - TROUBLESHOOTING LADDER. Apply one step at a time, re-testing after each, and stop at
the first that works. Report each attempt and its result, including the ones that failed.

  FIX 1 - groups/permissions (most common on a fresh install)
    The user was added to video/render in Step 5 but has not re-logged in. If /dev/kfd is
    root:render only, that alone explains "no GPU". Verify with `id` and report; the fix is a
    re-login, which the user does, not you.

  FIX 2 - ROCm version vs card support
    gfx1201 (RDNA4) needs a recent ROCm (7.x). If rocminfo lists older targets only, check:
      pacman -Q | grep -i rocm
      /opt/rocm/bin/rocminfo | grep -E 'Name|gfx|Marketing'
    If the card is absent entirely, the installed ROCm is too old for RDNA4. Report the exact
    version and move to FIX 5 (Docker), which pins a known-good combination.

  FIX 3 - HSA override (only if the card is detected but agents are empty/unsupported)
    gfx1201 maps to HSA version 12.0.1. Try:
      HSA_OVERRIDE_GFX_VERSION=12.0.1 /opt/rocm/bin/rocminfo | head -40
    and the same env var in front of the PyTorch test. This is a mitigation, not a fix -
    say clearly that it worked around the problem and what it masked.

  FIX 4 - Secure Boot / IOMMU
    If /dev/kfd is missing entirely and dmesg shows nothing for amdgpu:
      sudo dmesg | grep -iE 'kfd|iommu|secure boot' | tail -20
      mokutil --sb-state 2>/dev/null
    Secure Boot blocking the module and restrictive IOMMU groups are both real causes. Report
    what you find and propose the specific change (do NOT edit bootloader config or disable
    Secure Boot without the user's explicit approval).

  FIX 5 - Docker with AMD's official image (the reliable fallback)
      sudo pacman -S --needed --noconfirm docker docker-compose
      sudo systemctl enable --now docker
      sudo usermod -aG docker "$USER"
      sudo docker pull rocm/pytorch:rocm7.14_ubuntu24.04_py3.11_pytorch_release_2.10.0
      sudo docker run --rm --device=/dev/kfd --device=/dev/dri \
          --group-add video --group-add render \
          -e PYTORCH_TUNABLEOP_ENABLED=1 \
          rocm/pytorch:rocm7.14_ubuntu24.04_py3.11_pytorch_release_2.10.0 \
          python -c "import torch; print(torch.__version__); print('cuda available:', torch.cuda.is_available()); print(torch.cuda.get_device_name(0) if torch.cuda.is_available() else 'NO GPU')"
    This route is container-isolated, so it sidesteps host ROCm version mismatches entirely.
    If it works, RUN ALL TRAINING IN THIS CONTAINER and record the exact command in the report.

  FIX 6 - verify it is real, not just "available"
    Whatever route worked, prove the GPU actually computes:
      python - <<'EOF'
      import torch, time
      a = torch.randn(4096, 4096, device='cuda')
      torch.cuda.synchronize(); t0 = time.time()
      for _ in range(20): b = a @ a
      torch.cuda.synchronize(); dt = time.time() - t0
      print('device:', torch.cuda.get_device_name(0))
      print('GFLOP/s:', 20 * 2 * 4096**3 / dt / 1e9)
      EOF
    A real RDNA4 result is in the thousands of GFLOP/s. A tiny number or an error means the
    "available: True" was not real. Report the measured GFLOP/s.

6d - IF NOTHING WORKS
  Do not fake it and do not proceed silently. Report: which fixes were tried, the exact
  errors, `rocminfo` output, dmesg lines, and your best hypothesis. The project can still start
  at P0 (which needs no GPU - it is photo replay and measurement), so say that the CPU-only
  path is usable and what it costs (no training, only evaluation).

Report which route finally worked, with the GFLOP/s number.
"cuda available: True" is the only acceptable proof.
